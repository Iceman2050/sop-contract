# SOP Contract Studio — Overlap Gate

**Date inspected:** 2026-11-11
**Question:** Does the proposed `sop-contract` repo (convert human-approved SOPs into executable agent acceptance tests) duplicate the existing EvalScope platform, in which case it must ship as an EvalScope expansion module instead of a separate repo?
**Inspection only.** Nothing was built or uploaded for this gate.

## Verdict

**PROCEED: sop-contract is a distinct repo**

EvalScope — renamed **EvalEgress** — is an **eval-to-prod boundary / data-egress exposure scanner**. It is not a business-procedure execution tester, and it does not cover the SOP Contract capability set. Of the seven comparison capabilities (a)–(g) below, EvalScope/EvalEgress covers **none in substance**; it has only two superficial analogues (a static-config analogue of forbidden-action detection, and an evidence-pack *form* analogue). That is well below the "covers most of (a)–(g)" threshold for an expansion-module ruling.

## Capability comparison — sop-contract spec vs EvalScope / EvalEgress

SOP Contract spec (from the proposal): a YAML contract per workflow defining Objective, Preconditions, Permitted tools, Required steps, Forbidden actions, Exception paths, Human escalation, Postconditions, Evidence; the toolkit validates the spec, generates acceptance test cases, runs tests against approved sandbox / read-only tools, checks required + forbidden actions, compares outcomes vs human-approved criteria, and produces an evidence report with unresolved cases.

| # | SOP Contract capability | EvalScope / EvalEgress | Evidence |
|---|---|---|---|
| (a) | Procedure / SOP spec as input (YAML with Objective, Preconditions, Permitted tools, Required steps, Forbidden actions, Exception paths, Human escalation, Postconditions, Evidence) | **No.** Input is pasted/uploaded repo file listings and config text. No spec schema, no YAML contract parser, no per-workflow fields of any kind. | `app/scanner.py` `scan_files([{path, content}])`; README "Paste a repo file listing or config text". Live `/docs`: "Declared input in, exposure report out." |
| (b) | Required-step verification (did the agent perform the steps the SOP requires, in scope/order?) | **No.** Nothing executes or observes an agent run. The scanner pattern-matches text lines for exposure classes; there is no step model to verify against. | `app/scanner.py` `_RULES` (16 regex classes only); `tests/test_scanner.py` has no step/run tests. |
| (c) | Forbidden-action detection (did the agent do something the SOP forbids during a run?) | **No — static analogue only.** It detects forbidden-*shaped configuration* in declared text (e.g. `wildcard_iam_action`, `admin_managed_policy`, `wildcard_principal`). It never observes an action, a tool call, or a run, and by design cannot: scan-only, no execution, no live probing. | README "SCAN-ONLY … Anything needing a live check is reported as a finding — never probed"; live homepage: "No live probing, ever … 0 Live systems touched". |
| (d) | Exception-path evaluation (does the agent follow the SOP's exception branches?) | **No.** No branching, no workflow paths, no execution. The escape pack's five checks are fixed containment vectors (DNS egress, side-service pivot, shared cache, shutdown/kill, monitor tamper), not exception paths from a user procedure. | `app/escape.py` `assess()` — exactly five hard-coded checks; `DECLARATION_FIELDS` limited to the five containment declarations listed above. |
| (e) | Human-escalation / approval-limit rules (e.g. amount over a limit → `require_approval`) | **No.** No amounts, thresholds, escalation rules, or approval semantics. The nearest concept, the Monitor Independence Check, asks only whether monitoring/kill controls are declared *outside* the agent's reachable scope — a containment question, not a per-workflow human-escalation rule. | `app/escape.py` `MONITOR_RULE` and `assess()` monitor-independence block; `DECLARATION_FIELDS` contains no amount/escalation field. |
| (f) | Ground-truth / outcome comparison (compare the run's outcome and postconditions against human-approved criteria) | **No.** There is no expected outcome to compare against. Scoring compares a scan against nothing — it subtracts fixed severity weights from 100. Evidence-pack statuses (`exposed` / `evidence` / `no_evidence`) describe whether containment controls were *declared*, not whether a procedure's postconditions held. | `app/scanner.py` `score_report()`; `app/escape.py` `STATUSES = ("exposed", "evidence", "no_evidence")` and the pack docstring: "A pack is containment evidence, never proof of safety." |
| (g) | Evidence report with unresolved cases | **Form analogue only, different substance.** EvalEgress does emit reports: the findings report and the hash-chained Containment Escape Evidence Pack (exportable JSON, Team plan). But the pack's contents are the scan's findings verbatim plus the five containment checks and an operator-declared containment log; its "unresolved" analogue, `no_evidence`, means "a containment control was not declared" — not "an acceptance test case could not be resolved". There are no generated test cases, so there are no unresolved cases to report. | `app/escape.py` `build_pack()` (copies score/grade/counts/findings verbatim from the scan report); routes `/app/evidence/{pid}` and `/app/evidence/{pid}/export` in `app/main.py`; README "Containment Escape Evidence Pack (Team)". |

**Score: 0 of 7 covered in substance; 2 of 7 have superficial analogues ((c) static-config detection, (g) evidence-pack form).**

## Conclusion

- The overlap suspect is cleared by its own source: EvalScope/EvalEgress answers *"what could an eval agent reach?"* by statically scanning declared configs for exposure. SOP Contract answers *"did the agent follow this approved procedure?"* by generating and running acceptance tests from an SOP spec. Different input (config text vs SOP YAML), different mechanism (regex pattern-matching vs test generation + sandbox/read-only tool execution), different output (exposure score vs per-case evidence with unresolved cases).
- **sop-contract PROCEEDS as its own repo.** It is not an EvalScope expansion module.
- Build-stage note (not part of the verdict): keep the boundary clean in the new repo's README — one line distinguishing it from EvalEgress (exposure scanning), HarnessProof (fixed harness scenario suites), and Agentic Receipts (authorization records) will prevent this same question being re-asked later.
